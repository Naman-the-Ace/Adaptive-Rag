# Adaptive RAG — Evaluation Framework

A production-grade evaluation suite for the Adaptive RAG system built with LangGraph, FAISS, and Groq/Gemini.

---

## Directory Structure

```text
evaluation/
├── datasets/
│   ├── golden_dataset.jsonl          # 60 labeled evaluation queries
│   └── sample_docs/
│       └── rag_concepts.txt          # Sample document for FAISS seeding
├── scripts/
│   ├── evaluate_retrieval.py         # Precision@K, Recall@K, MRR, nDCG, Hit Rate
│   ├── evaluate_generation.py        # LLM-as-judge: Faithfulness, Relevancy, Correctness
│   ├── evaluate_routing.py           # Routing accuracy, confusion matrix, F1 per route
│   ├── benchmark_latency.py          # Per-node and E2E latency statistics
│   ├── generate_plots.py             # Charts from actual result files
│   └── run_all.py                    # Master orchestrator
├── reports/                          # Auto-generated by scripts (gitignored outputs)
├── plots/                            # Auto-generated charts
├── config/
│   └── eval_config.yaml              # Configurable parameters
├── tests/
│   └── test_metrics.py               # Unit tests for metric functions
├── requirements.txt
└── README.md                         # This file
```

## Prerequisites

### 1. Python Environment

Use the same Python environment as the `adaptive_rag` project (Python 3.10+):

```bash
# Install adaptive_rag dependencies first
cd adaptive_rag
pip install -r requirements.txt

# Install evaluation-specific dependencies
pip install -r ../evaluation/requirements.txt
```

### 2. API Keys

Copy the `.env.example` to `.env` at the repo root and fill in your keys:

```bash
cp .env.example .env
```

| Variable | Required | Purpose |
|---|---|---|
| `GROQ_API_KEY` | **Required** (or Gemini) | LLM inference for RAG pipeline and judge |
| `GEMINI_API_KEY` | Fallback | Used if GROQ_API_KEY is not set |
| `TAVILY_API_KEY` | Optional | Required for search-route queries |
| `MONGODB_URL` | Optional | Chat history (disabled in eval mode) |

> **Note:** The evaluation framework uses the same LLM as the application. No separate judge API key is needed.

### 3. Documents

The framework includes a sample document (`evaluation/datasets/sample_docs/rag_concepts.txt`) covering RAG concepts. You can substitute or add your own documents.

## Quick Start

All evaluation scripts must be run **from the `adaptive_rag/` directory** so the app's Python path resolves correctly:

```bash
cd adaptive_rag

# 1. Run unit tests only (no API keys needed)
python -m pytest ../evaluation/tests/test_metrics.py -v

# 2. Run retrieval evaluation (no generation LLM calls)
python ../evaluation/scripts/evaluate_retrieval.py \
    --dataset ../evaluation/datasets/golden_dataset.jsonl \
    --doc     ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --k 3 5 10

# 3. Run all evaluations (retrieval + routing + latency)
python ../evaluation/scripts/run_all.py \
    --doc ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --skip-generation

# 4. Full run including LLM-as-judge generation evaluation:
python ../evaluation/scripts/run_all.py \
    --doc ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --generation-sample 15

# 5. Generate plots from existing results
python ../evaluation/scripts/generate_plots.py
```

## Evaluation Scripts Reference

### `evaluate_retrieval.py`

Computes deterministic retrieval metrics from FAISS similarity search results.

```bash
python ../evaluation/scripts/evaluate_retrieval.py \
    --dataset ../evaluation/datasets/golden_dataset.jsonl \
    --doc     ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --k 3 5 10 \
    --output  ../evaluation/reports/retrieval_results.csv

# With query rewriting enabled:
python ../evaluation/scripts/evaluate_retrieval.py ... --rewriting
```

**Outputs:**
- `retrieval_results.csv` — per-query metrics
- `retrieval_results_aggregate.json` — mean Precision@K, Recall@K, Hit Rate@K, MRR, nDCG@K

### `evaluate_routing.py`

Runs every query through the LangGraph pipeline and compares predicted route against expected route.

```bash
python ../evaluation/scripts/evaluate_routing.py \
    --dataset ../evaluation/datasets/golden_dataset.jsonl \
    --doc     ../evaluation/datasets/sample_docs/rag_concepts.txt
```

**Outputs:**
- `routing_results.csv` — per-query predictions
- `routing_results_summary.json` — accuracy, per-route F1, confusion matrix

### `benchmark_latency.py`

Measures latency statistics for each pipeline node.

```bash
python ../evaluation/scripts/benchmark_latency.py \
    --doc   ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --runs  10 \
    --warmup 2

# Skip LLM-dependent benchmarks (embedding + FAISS only):
python ../evaluation/scripts/benchmark_latency.py ... --skip-llm
```

**Outputs:**
- `latency_results.csv` — mean, median, p90, p95, p99, min, max per component
- `latency_results.json`

### `evaluate_generation.py`

LLM-as-judge evaluation of generation quality.

```bash
python ../evaluation/scripts/evaluate_generation.py \
    --dataset ../evaluation/datasets/golden_dataset.jsonl \
    --doc     ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --sample  20

# With RAGAS (requires: pip install ragas datasets):
python ../evaluation/scripts/evaluate_generation.py ... --ragas
```

**Outputs:**
- `generation_results.csv` — per-query scores
- `generation_results_aggregate.json`
- `failure_analysis.md`

> ⚠ All generation scores are LLM-as-judge (not independently verified ground truth).

### `run_all.py`

Orchestrates all evaluation phases and generates `evaluation_summary.md`.

```bash
python ../evaluation/scripts/run_all.py \
    --doc ../evaluation/datasets/sample_docs/rag_concepts.txt \
    --k 3 5 10 \
    --latency-runs 10 \
    --generation-sample 15 \
    --ragas   # optional
```

## Metric Definitions

### Retrieval Metrics (Deterministic)

| Metric | Definition | Range |
|---|---|---|
| **Precision@K** | \|relevant ∩ top-K\| / K | [0, 1] |
| **Recall@K** | \|relevant ∩ top-K\| / \|relevant\| | [0, 1] |
| **Hit Rate@K** | 1 if any relevant in top-K, else 0 | {0, 1} |
| **MRR** | mean(1 / rank of first relevant) | [0, 1] |
| **nDCG@K** | DCG@K / IDCG@K (graded relevance) | [0, 1] |

### Generation Metrics (LLM-as-Judge)

| Metric | Definition | Range |
|---|---|---|
| **Faithfulness** | Fraction of answer claims supported by context | [0, 1] |
| **Answer Relevancy** | How well the answer addresses the question | [0, 1] |
| **Answer Correctness** | Factual match vs reference answer | [0, 1] |
| **Context Precision** | Fraction of retrieved context that is relevant | [0, 1] |
| **Context Recall** | Fraction of needed information present in context | [0, 1] |
| **Hallucination Rate** | Fraction of queries with faithfulness < 0.5 | [0, 1] |

## Dataset: `golden_dataset.jsonl`

**Format:** JSON Lines — one JSON object per line.

**Schema:**
```json
{
    "query_id": "DOC-001",
    "question": "What is RAG?",
    "expected_route": "index",
    "reference_answer": "RAG is ...",
    "relevant_doc_ids": ["rag_concepts.txt"],
    "relevant_chunk_ids": [],
    "difficulty": "easy",
    "category": "factual",
    "verified": false,
    "notes": "UNVERIFIED - check against ingested doc"
}
```

**Distribution:**
- 40 document-route queries (`expected_route: "index"`)
- 10 general-knowledge queries (`expected_route: "general"`)
- 10 web-search queries (`expected_route: "search"`)

> **Important:** Most document-route queries have `verified: false` and `relevant_doc_ids: []`.
> After ingesting your real documents, update `relevant_doc_ids` with the actual source filenames
> to get valid retrieval metrics. Queries with empty `relevant_doc_ids` will score 0 on
> Precision@K, Recall@K, MRR, and nDCG.

### How to Update Ground Truth Labels

1. Ingest your documents via the RAG API
2. Run retrieval for each query and inspect the returned documents
3. Update `relevant_doc_ids` with the correct source filenames
4. Set `verified: true` for confirmed labels
5. Re-run `evaluate_retrieval.py` for valid metrics

## Reproducibility

Each evaluation run records:
- Timestamp in the summary report
- Dataset file and version
- Document paths ingested
- K values evaluated
- LLM configuration (from environment variables)
- Sample size for generation evaluation

To reproduce a run, use the same:
1. `.env` configuration (same GROQ_API_KEY / GEMINI_API_KEY)
2. Dataset file (commit `golden_dataset.jsonl` to version control)
3. Document files in `sample_docs/`
4. Same K values and sample size arguments

> **Limitation:** LLM-as-judge scores vary slightly between runs due to LLM non-determinism even at temperature=0.1. Report mean ± stdev over multiple runs for robust estimates.

## Important Disclaimers

1. **No fabricated scores** — All reported metrics come from actual experiment runs.
2. **Unverified labels** — Document-route queries have `verified: false` until manually reviewed.
3. **LLM-as-judge** — Generation metrics are estimates, not ground truth.
4. **In-memory FAISS** — The index is lost on restart; documents must be re-ingested each run.
5. **Web search excluded** — Search-route generation is not evaluated here as results vary over time.
6. **No reranking** — The existing pipeline does not implement reranking; it is noted as a future improvement only.

## Future Improvements

Based on the evaluation framework design, potential improvements to explore:

1. **Persistent FAISS index** — Save/load the index to skip re-ingestion on each run
2. **Reranking** — Add a cross-encoder reranker after FAISS retrieval (e.g., `cross-encoder/ms-marco-MiniLM-L-6-v2`)
3. **Chunk size optimization** — Compare 500/1000/1500 char chunk sizes
4. **Higher K retrieval** — Retrieve K=10 and let the grader filter, improving recall
5. **Metadata filtering** — Filter by document source before similarity search
6. **RAGAS integration** — Use `pip install ragas` for standardized metric computation
